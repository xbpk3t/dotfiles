# 3w3h — 3W3H 框架


Why  ->  What  <->  When/where?
How to use?
How to implement?
How to optimize?

帮我结合这个 3W3H 介绍一下

需要注意的是，并非3w3H的每个部分只有一个问题，可以有多个问题

---

另外，在此之后，还需要再给我一个 YAML codeblock，格式类似



请严格按照以下要求生成YAML格式的技术选型分析：
## **强制结构**

- 包含6个固定字段：`why`、`what`、`ww`、`htu`、`hti`、`hto`
- 字段顺序必须为：why → what → ww → htu → hti → hto

## **内容规范**


- 所有字段值必须为**数组格式**
- 每个数组项应以 问题的形式 表现，【】标注核心关键词开头（如【核心功能】），最终格式为：【核心关键字】问题？简要回答
- 禁止出现嵌套key（如"自建中继: xxx" 改为【自建中继】xxx）

## **数据要求**

各字段语义锚定：


- `why`：为什么要用这个？（痛点 + 价值）
- `what`：这是什么？（功能定义 + 技术分类）
- `ww`：什么时候用？（适用场景 + 局限性）
- `htu`：怎么上手？（选型决策 → 安装配置 → 基本使用）
- `hti`：怎么实现的？（核心原理 → 架构流程 → 关键实现细节）
- `hto`：怎么优化？（性能调优 → 常见坑 → 安全加固 → 运维建议）

### 边界说明


htu 是使用者视角「怎么装怎么用」，hti 是开发者视角「内部怎么实现的」，hto 是运维者视角「怎么让它更好用」。

同一个话题：

htu 讲 CLI 用法，hti 讲架构原理，hto 讲性能坑。



### 数量

每个字段至少3条（3-5条）



### 细节


对于 `【breakdown】`：先执行 pipeline 中的 `brk`（[references/analysis/brk.md](references/analysis/brk.md)），将定义式与分项表纳入 hti 里对应 item。

对于 `【技术选型】` 项：先执行 pipeline 中的 `vs`（[references/repo/vs.md](references/repo/vs.md)），再将对比结论总结为此项的答案。注意需要把这个对比本身的 table，也单独列出。




## **输出示例**

每条问题后面用 `#` 注释写明答案，格式为：

```yaml

- topic: <topic-name>
  why:
    - 【meta】 # 这个技术属于哪个更大的范畴？
    - 【存在之必要】这个场景下到底要解决什么问题？ # 例如：服务器之间没有公网IP，无法直连
    - 【技术选型】相较于其他严格对标的相应服务/工具，其核心优势在于什么？ # 先完成 vs 对比后的结论摘要
  what:
    - 【核心功能】一句话概括它是做什么的
    - 【技术分类】属于哪个技术范畴或品类
    - 【关键特性】区别于同类产品的核心差异
  ww:
    - 【适用场景】最适合在什么情况下使用？
    - 【不适用场景】什么情况下不应该用它？
    - 【前置条件】使用它需要什么前提？
  htu:
    - 【选型决策】根据什么条件判断该用哪个？
    - 【快速开始】最小可用的安装和配置步骤
    - 【基本使用】日常最常用的操作方式
  hti:
    - 【breakdown】
    - 【核心原理】它的工作机制是什么？
    - 【架构流程】关键链路的数据流转
    - 【关键实现】最值得了解的实现细节
  hto:
    - 【性能优化】哪些配置或手段能提升性能？
    - 【避坑指南】新手最容易踩的坑
    - 【运维建议】长期维护需要注意什么？

```
